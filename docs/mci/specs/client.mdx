## Overview

The MCI client is the layer that wraps a large language model (LLM). Its job is to bridge the model's expressed intent and the MCI server that executes it. The client observes model output, extracts executable intent from it, submits that intent to the MCI server, and feeds execution results back to the model.

The client does not execute code itself. It is purely a translation and communication layer.

The client has three core responsibilities:

**Intent Extraction** — The client monitors model output and detects when the model is expressing an intent to execute code. The extracted intent must include the code to be executed and the metadata that describes it. How detection works is implementation-defined.

**Request Submission** — The client creates a template via `POST /templates`, then immediately creates a process against that template via `POST /processes`. The client is responsible for correctly formatting both requests.

**Result Retrieval and Relay** — The client polls the MCI server for process status and output. Once execution completes, it retrieves the results and presents them back to the model. How results are relayed to the model is implementation-defined.

---

## Intent Extraction

How a client detects model intent is left to the implementer. The MCI project recommends the following convention, but it is not required.

### Recommended Convention: Annotated Code Blocks

The model outputs a fenced code block with three parts on the opening line:

~~~
```<language> mci <key=value pairs>
<code>
```
~~~

- `<language>` is any language identifier (e.g. `ts`, `python`, `js`)
- `mci` is the intent marker — its presence signals that this block is an MCI execution request
- `<key=value pairs>` are template metadata fields, space-separated

**Example:**

~~~
```ts mci name=fetch-user description="Fetch a user by ID" environment=deno
const res = await fetch("https://api.example.com/users/1");
const user = await res.json();
dispatch({ output: user });
```
~~~

When a client sees the `mci` keyword after the language identifier, it treats the block as an execution request. The key-value pairs are parsed as template metadata. The body of the block is the code.

Clients may use any other mechanism for intent extraction — XML tags, structured JSON output, a dedicated system prompt protocol, etc. The extraction mechanism does not affect how requests are submitted to MCI. Only the final request shapes matter.

Clients should handle malformed or incomplete metadata gracefully, either by rejecting the block with an error to the model or by applying defaults where applicable.

## Core Concepts

MCI separates the definition of code from its execution. These are two distinct concerns managed by two distinct resources.

### Template

A template is a definition — code and everything that describes it. Templates are inert. Creating a template does not execute anything. A template can exist indefinitely without ever being executed.

Templates are mutable. The `code`, `environment`, `name`, and `description` fields can be updated at any time. The `lint` and `save` flags are **creation-only** — they are set when the template is created and cannot be changed afterwards. If different lint or save behaviour is needed, create a new template.

### Process

A process is an execution request against a template. Creating a process queues it for execution immediately. A process carries the execution-specific configuration and owns the execution result — state, status, and outputs.

A template can be the basis for multiple processes over time. A process always references exactly one template.

### The Snapshot Contract

> **This is the most important invariant in MCI.**
>
> When a process is created, it takes a snapshot of the template at that exact moment — the code, environment, name, and description are copied into the process and stored independently. The process never references the live template again after this point.
>
> This means updating or deleting a template has no effect on any process already created from it. A running process always completes against the code it was started with, regardless of what happens to its source template afterwards.
>
> Every process is a fully self-contained execution record. Its `tid` field records which template it originated from, but it does not depend on that template continuing to exist or remain unchanged.

### Identifiers

- **TID** — Template ID. Assigned on `POST /templates`
- **PID** — Process ID. Assigned on `POST /processes`

## Templates

Templates live at `/templates` and support listing, creation, retrieval, partial update, and deletion.

---

### `GET /templates`

List all templates available in the current session, including persistent templates.

**Query parameters (all optional):**

| Parameter | Type | Description |
|---|---|---|
| `name` | string | Filter by name (exact match) |
| `environment` | string | Filter by environment prefix |
| `save` | boolean | `true` returns persistent templates only, `false` returns session-scoped only |

**Response:**

```json
{
  "templates": [
    {
      "tid": "string",
      "name": "string | null",
      "description": "string | null",
      "environment": "string",
      "lint": "boolean",
      "save": "boolean",
      "created_at": "ISO 8601 timestamp"
    }
  ]
}
```

`code` is not included in list responses. Use `GET /templates/:tid` to retrieve the full template including code.

---

### `POST /templates`

Create a new template. If `lint` is `true`, the code is linted before the template is saved. If linting fails, the template is not created and the lint output is returned instead.

**Request body:**

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `code` | string | yes | — | The code to be executed when a process is created from this template |
| `environment` | string | yes | — | The target sandbox environment. Supports prefix matching (e.g. `python` matches all Python environments, `python3` matches only Python 3 environments) |
| `name` | string | no | — | Human-readable name for querying and identification |
| `description` | string | no | — | Human-readable description for querying and identification |
| `lint` | boolean | no | `false` | **Creation-only.** If true, code is linted before saving. Lint failure prevents creation and returns lint output. Cannot be changed after creation |
| `save` | boolean | no | `false` | **Creation-only.** If false, the template is session-scoped. If true, it persists across server restarts. Cannot be changed after creation |

**Response (success):**

```json
{
  "tid": "string",
  "name": "string | null"
}
```

**Response (lint failure):**

```json
{
  "error": "lint_failed",
  "output": "string"
}
```

---

### `GET /templates/:tid`

Retrieve a template's full definition including code.

**Response:**

```json
{
  "tid": "string",
  "name": "string | null",
  "description": "string | null",
  "code": "string",
  "environment": "string",
  "lint": "boolean",
  "save": "boolean",
  "created_at": "ISO 8601 timestamp"
}
```

---

### `PATCH /templates/:tid`

Update a template. Supports partial updates — only include the fields you want to change. Only `code`, `environment`, `name`, and `description` may be patched. The `lint` and `save` flags are creation-only and cannot be updated.

If the template was created with `lint: true` and the patch includes a `code` update, the new code is linted before the update is applied. If linting fails, the template is not updated.

Updates affect future processes only. Existing processes are independent snapshots and are completely unaffected by any template update — including patches to `code` or `environment` while a process is actively running.

**Request body (all fields optional):**

```json
{
  "code": "string",
  "environment": "string",
  "name": "string",
  "description": "string"
}
```

**Response (success):** Updated template object, same shape as `GET /templates/:tid`.

**Response (lint failure):**

```json
{
  "error": "lint_failed",
  "output": "string"
}
```

---

### `DELETE /templates/:tid`

Delete a template. If the template is persistent (`save: true`), it is also removed from persistent storage. Existing processes created from this template are completely unaffected — they are independent snapshots.

**Response:** `204 No Content`

---

## Processes

Processes live at `/processes`. Creating a process immediately queues it for execution against the referenced template.

---

### `GET /processes`

List all processes in the current session.

**Query parameters (all optional):**

| Parameter | Type | Description |
|---|---|---|
| `tid` | string | Filter by template ID |
| `state` | string | Filter by state (`queued`, `running`, `idle`) |
| `status` | string | Filter by status (`success`, `failed`) |

**Response:**

```json
{
  "processes": [
    {
      "pid": "string",
      "tid": "string",
      "state": "queued | running | idle",
      "status": "success | failed | null",
      "created_at": "ISO 8601 timestamp"
    }
  ]
}
```

---

### `POST /processes`

Create a new process. The process is queued for execution immediately upon creation.

**Request body:**

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `tid` | string | yes | — | The TID of the template to execute |
| `envconf` | object | no | `{}` | Arbitrary key-value configuration passed to the sandbox, such as memory limits or thread constraints |
| `timeout` | number/null | no | `null` | Execution timeout in milliseconds. `null` means no timeout |
| `retries` | number/null | no | `3` | Number of retry attempts on failure. `null` means no retries |

**Response:**

```json
{
  "pid": "string",
  "tid": "string"
}
```

---

### `GET /processes/:pid`

Retrieve the state and status of a process.

**Response:**

```json
{
  "pid": "string",
  "tid": "string",
  "state": "queued | running | idle",
  "status": "success | failed | null",
  "envconf": "object",
  "timeout": "number | null",
  "retries": "number | null",
  "created_at": "ISO 8601 timestamp"
}
```

`status` is `null` while the process has not yet completed.

---

### `POST /processes/:pid/signals/:signal`

Send a signal to a process. See [Signals](#signals) for valid signal names and constraints.

**Request body:** `{}` (signals do not currently require a body)

**Response:** Signal-dependent. See Signals section.

---

## Process Lifecycle

A process moves through three states:

| State | Meaning |
|---|---|
| `queued` | Waiting to run. Scheduled but blocked on sandbox availability |
| `running` | Actively executing |
| `idle` | Not running. Execution has completed or the process was killed |

Transitions are linear and one-way:

```
queued → running → idle
```

A process begins in `queued` the moment it is created. Once it reaches `idle` it does not transition again. To re-run the same template, create a new process.

Status records the outcome of a completed execution and is only set once a process reaches `idle`:

| Status | Meaning |
|---|---|
| `null` | Process has not yet completed |
| `success` | Process completed without error |
| `failed` | Process encountered an error or was killed |

The combination of state and status fully describes a process's position in its lifecycle:

| State | Status | Meaning |
|---|---|---|
| `queued` | `null` | Waiting for sandbox |
| `running` | `null` | Actively executing |
| `idle` | `success` | Completed successfully |
| `idle` | `failed` | Completed with failure or was killed |

---

## Signals

Signals are sent to processes via `POST /processes/:pid/signals/:signal`. Signals are never sent to templates.

### `kill`

Stops a process that is currently running or queued. The process transitions to `idle` with status `failed`.

**Valid states:** `running`, `queued`

**Response:**

```json
{
  "pid": "string",
  "state": "idle",
  "status": "failed"
}
```

---

## Querying Outputs

Outputs are scoped to processes and do not require execution to be complete — partial stdout and stderr may be available while a process is still running.

| Endpoint | Returns |
|---|---|
| `GET /processes/:pid/outputs` | All outputs as a structured object |
| `GET /processes/:pid/stdout` | Standard output as plain text |
| `GET /processes/:pid/stderr` | Standard error as plain text |

**`GET /processes/:pid/outputs` response:**

```json
{
  "stdout": "string",
  "stderr": "string",
  "dispatches": []
}
```

Outputs are cache-managed alongside their process and evicted together. If long-term output retention is needed, the client is responsible for reading and storing outputs before eviction.

---

## Future Considerations

**Snapshot inspection.** It would be useful for clients to query the exact code and metadata a process was created with, independently of whatever the source template currently looks like. A `GET /processes/:pid/snapshot` endpoint would serve this purpose and is a candidate for a future revision of this specification.

---

## Client Implementation Notes

**The client owns both requests.** When the model expresses intent, the client makes two sequential requests — `POST /templates` to register the code, then `POST /processes` to queue execution. These are always two separate calls.

**Template reuse is the client's decision.** A client may cache TIDs and reuse or update a previously created template rather than creating a new one every time. Whether and how to do this is an implementation concern not covered by this specification.

**Result relay is implementation-defined.** How the client presents process outputs back to the model — inline, as a message, as a tool result, or otherwise — is left to the implementer.

**Polling is the recommended pattern.** The client should poll `GET /processes/:pid` until `state` is `idle` and `status` is non-null, then retrieve outputs.

**Environment resolution is the client's responsibility.** The `environment` field must be provided by the client. When using the recommended code block convention, the language identifier is the natural source for this value.

**Session-scoped templates do not survive server restarts.** If templates need to persist, `save` must be set to `true` at creation time. This cannot be changed after creation.
